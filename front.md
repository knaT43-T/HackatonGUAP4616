# Frontend «Слушаем вместе» — документация

SPA для совместного прослушивания музыки: **Vue 3 + Vite**. Светлая тема, роутинг, REST API и WebSocket-синхронизация. Комната живёт на сервере, клиент держит состояние и пересчитывает позицию сам.

> **Статус реализации.** Готово всё MVP: вход по нику, приватные маршруты, создание комнаты и вход по коду, плеер с синхронным воспроизведением, очередь, каталог с загрузкой треков, live-обновления по WebSocket (разделы 10–14).

---

## 2. Быстрый старт

```bash
cd frontend
npm install
npm run dev
```

Открывается `http://localhost:5173`

**Переменные окружения**

Все переменные необязательны: если `.env` нет, используются адреса
`http://<хост страницы>:8000` и `ws://<хост страницы>:8000/ws` (см. `src/config.js`).
Для нестандартной конфигурации скопируй `frontend/.env.example` в `frontend/.env`:

```
VITE_API_URL=http://127.0.0.1:8000
VITE_WS_URL=ws://127.0.0.1:8000/ws
```

**Скрипты**

| Команда | Что делает |
|---|---|
| `npm run dev` | Dev-сервер Vite, порт 5173 |
| `npm run build` | Prod-сборка в `dist/` |
| `npm run preview` | Просмотр `dist/` локально |

| Путь | Компонент | Доступ | Что показывает |
|---|---|---|---|

Гард `router.beforeEach` пропускает дальше только при живой сессии: один раз

Если сессии нет — редирект на `/` с `?redirect=<исходный путь>`, чтобы после
входа вернуть человека туда, куда он шёл.

## 5. API

`src/api/client.js` — **реализовано**

Единая обёртка над `fetch`. Задачи:

- приложить cookie (`credentials: 'include'`) — без этого бэкенд не узнает человека;
- выставить `Content-Type: application/json` (для `FormData` не трогать: браузер сам поставит boundary);
- при `!res.ok` выбросить `ApiError` со статусом, текстом и кодом ошибки.

Экспорты: `api` — базовый вызов, `ApiError` — класс ошибки.

`src/api/auth.js`

| Функция | HTTP | Описание |
|---|---|---|
| `loginGuest(nickname)` | `POST /api/auth/guest` | Получает cookie `pid` |
| `getMe()` | `GET /api/auth/me` | Текущий участник |

`src/api/rooms.js`

| Функция | HTTP |
|---|---|
| `createRoom(name)` | `POST /api/rooms` |
| `joinRoom(inviteCode)` | `POST /api/rooms/join` |
| `leaveRoom(roomId)` | `POST /api/rooms/{room_id}/leave` |

`src/api/tracks.js`

| Функция | HTTP |
|---|---|
| `listTracks()` | `GET /api/tracks` |
| `uploadTrack(file, {title, artist})` | `POST /api/tracks/upload` (multipart) |

`src/api/queue.js`

| Функция | HTTP |
|---|---|
| `addToQueue(roomId, trackId)` | `POST /api/rooms/{room_id}/queue` |

Добавление в очередь — REST: сервер сам разошлёт `queue_update` всем в комнате.
Удаление — командой `queue_remove` по сокету (только host, см. раздел 10).

## 6. Аутентификация

**Хранение**

Никаких токенов. Только cookie `pid`, выставленная бэкендом. Браузер прикладывает её сам ко всем запросам с `credentials: 'include'` и к WebSocket. Фронту не нужно ничего хранить и прикладывать вручную.

**Состояние — `src/state/auth.js`**

- `auth.user` — `{ participant_id, nickname }` или `null`;
- `ensureSession()` — один раз проверяет `GET /api/auth/me` и кэширует результат;
- `signIn(nickname)` — `POST /api/auth/guest` и запись пользователя;
- `signOut()` — очистка клиентского состояния.

**Поток «гость → комнаты»**

1. Пользователь вводит ник на `/` (2–32 символа).
2. `signIn()` вызывает `loginGuest(nickname)`.
3. Cookie ставится бэкендом автоматически.
4. Редирект на `?redirect=...` или `/rooms`. Если сессия уже была жива, редирект срабатывает сразу при открытии `/`.

**Logout**

Отдельного эндпоинта на бэкенде нет: `signOut()` + редирект на `/`. Cookie
остаётся, поэтому после полной перезагрузки страницы человек снова узнаётся —
ограничение MVP; при необходимости добавим `POST /api/auth/logout`.

## 8. Страницы

`HomeView.vue` — `/`

Вход по нику. По успеху — переход на `?redirect=...` или `/rooms`. Отдельной страницы `/login` нет: главная и есть логин. Если сессия уже жива — сразу редирект в комнаты.

`RoomsView.vue` — `/rooms` — **реализовано**

- «Создать комнату» → `POST /api/rooms` → переход в `/room/:inviteCode`.
- «Войти по коду» → `POST /api/rooms/join` → переход в комнату.
- Обработка 404 («комната не найдена») и 401 (сессия протухла → на главную).

`RoomView.vue` — `/room/:inviteCode`

При монтировании открывает WebSocket и шлёт `join` с `invite_code`; до `snapshot` показывает экран загрузки, после — плеер, очередь, приглашение и участников. Live-обновления приходят по сокету, кнопки управления видит только host. «Выйти из комнаты» рвёт сокет и вызывает `POST .../leave` (сервер передаст хоста, если это были мы). Если комната не существует — экран «Комната не найдена»; если сессия умерла (закрытие 4401) — `signOut()` и редирект на `/`.

`NotFound.vue` — `*`

Показывает 404 и кнопку «На главную».

## 10. WebSocket

`src/ws/client.js` — тонкий транспорт: подключение, `join`, ping-цикл, reconnect. Бизнес-логики не содержит — события уходят в колбэк, статус соединения — в `onStatus`.

Подключение: `VITE_WS_URL` или `ws://<хост страницы>:8000/ws`. Cookie `pid` браузер прикладывает сам.

**Порядок работы:**

1. Открыли сокет — отправляем `join` (с `room_id` или `invite_code`).
2. Получили `joined` — сохранили `role` и `participant_id`.
3. Получили `snapshot` — заменили `room`, `state`, `queue`, `members` целиком.
4. Дальше реагируем на события: `state`, `queue_update`, `members_update`, `system`, `error`.

**Команды клиента — всё через сокет.** REST для управления плеером не используется:

| Команда | Кто | Что делает |
|---|---|---|
| `play` | host | Запустить / продолжить |
| `pause` | host | Пауза |
| `seek` | host | Перемотка |
| `skip` | host | Следующий трек |
| `queue_remove` | host | Убрать из очереди |
| `track_loaded` | любой | Сообщить длительность |
| `ping` | любой | Мерка часов |
| `leave` | любой | Выйти из комнаты |

**Коды закрытия**

| Код | Что делать |
|---|---|
| `4401` | Сессии нет — очистить состояние, увести на главную (`/`) |
| `4404` | Сокет вытеснен новой вкладкой — не переподключаться, показать нейтральный экран |

**Диспетчер событий** — один `switch` по `msg.type` в `src/state/room.js`. Каждый кейс — маленькая функция. Не разбирать одно событие в разных местах приложения.

## 11. Синхронизация

`src/ws/clock.js`

Смещение часов меряется через `ping/pong`: кандидат `server_time - (client_time + rtt/2)`. Держится скользящее окно последних 8 замеров, берётся замер с минимальным RTT — так меньше сказывается сетевая задержка.

- `ping` — сразу после `join`, затем каждые 4 секунды.
- После `visibilitychange` (возврат на вкладку) — `ping` немедленно.
- После reconnect — `ping` немедленно, старый `clockOffset` может быть неактуален.

`src/ws/position.js`

Позиция не хранится в стейте, а считается на каждый кадр:

```
position = is_playing
  ? position_ms + (now_server - updated_at)
  : position_ms
```

Где `now_server = Date.now() + clockOffset`.

`src/components/Player.vue`

- Пришёл `state` с новым якорем — выставляем `audio.currentTime` из `positionNow(state)`.
- Если `state.is_playing` — включаем воспроизведение, иначе ставим на паузу.
- Смена `state.item_id` — новый `<audio src>` (из `mediaUrl(track.url)`); сик и play делает `loadedmetadata`.
- Каждые 2 секунды сверяем реальную позицию `<audio>` с расчётной: расхождение > 2 с — жёсткий сик, 300 мс — 2 с — мягкая подтяжка `playbackRate` (±4%), меньше 300 мс — не трогаем. Так «сдвиг» не слышен.
- Если браузер заблокировал автозапуск (`play()` отклонён) — показываем кнопку «Включить звук».

**Частая ошибка:** выставлять позицию по `state.position_ms` без пересчёта. Между событием и его обработкой проходит время — трек уедет назад.

## 12. Длительность и автопереключение

Сервер не читает длительность из файла. Её сообщает клиент, у которого загрузился `<audio>`:

- по событию `loadedmetadata` отправляем `track_loaded` с `item_id` и `duration_ms`.

`item_id` — это id элемента **очереди**, не трека. Бери из `state.item_id`. Отправлять может кто угодно, достаточно один раз на трек.

**Без этого автопереключение не работает.** Сервер не знает, что трек кончился, и не перейдёт к следующему сам. Ручной `skip` работает всегда.

Отправлять повторно при каждой смене `state.item_id` — `<audio>` перезагружает новый источник, и `loadedmetadata` срабатывает заново.

## 13. Права в UI

| Действие | host | listener |
|---|:---:|:---:|
| play / pause / seek / skip | ✅ | ❌ |
| Убрать трек из очереди | ✅ | ❌ |
| Добавить трек в очередь | ✅ | ✅ |
| Слушать | ✅ | ✅ |

Правила:

- Кнопки `play/pause/seek/skip` и удаление из очереди видит только host.
- Для listener их не показываем вовсе («🎧 Управляет хост»), а не дизейблим — интерфейс чище. Громкость — локальная настройка, она есть у всех.
- Бэкенд всё равно проверит права и вернёт `forbidden` — ошибка приходит событием `error` и показывается тостом.
- Роль приходит в `joined` и меняется в `members_update` (два хоста не бывает — при передаче прав старый понижается). Держим `role` в состоянии комнаты, не пересчитываем вручную из списка участников.

## 14. Reconnect и уход хоста

**Reconnect** — `src/ws/client.js`

- Сокет закрылся не по `4401`/`4404` — переводим состояние в `reconnecting`, в шапке комнаты чип «переподключаемся…».
- Переподключение с backoff: 1s, 2s, 4s, 8s, максимум 15s.
- После открытия — снова `join`, `snapshot` заменяет `room`, `state`, `queue`, `members` целиком.
- Сразу `ping` — обновить `clockOffset`.
- `4401` — не переподключаться: `signOut()` и редирект на `/`.
- `4404` — не переподключаться: показываем нейтральный экран «комната открыта в другой вкладке».

Во время reconnect плеер продолжает играть локально. `<audio>` не останавливаем — иначе на каждой потере связи будет пауза.

**Ушёл хост.** Права переходят первому подключённому слушателю. Прилетает `members_update` с новой ролью и `system` с текстом «Управление передано: Петя» — показываем тостом. Если права перешли тебе — `role` обновится сам, кнопки появятся.

**Хост вернулся.** Создатель комнаты (`creator_id`) снова становится host, когда открывает WS в комнате. Ничего делать не нужно — достаточно открыть ту же ссылку.

**Пустая комната.** Музыка на паузе, комната живёт `ROOM_IDLE_TTL_MIN` (30 минут), потом удаляется. Если при `join` приходит `room_not_found` — показываем экран «Комната не найдена» без переподключений.

## 15. Типичные ошибки

| Ошибка | Причина | Решение |
|---|---|---|
| Failed to resolve import | Опечатка или файла нет | Проверить путь |
| X is not defined | Забыл импорт | Добавить `import X` |
| Failed to resolve component | Компонент не импортирован/опечатка в теге | Проверить импорт и имя тега |
| CORS policy | Бэкенд не разрешил origin | Добавить origin в `CORS_ORIGINS` |
| ERR_CONNECTION_REFUSED | Бэкенд не запущен | Запустить backend |
| Стили не применяются | `index.css` не импортирован | Проверить `main.js` |
| `VITE_API_URL undefined` | `.env` не в корне или Vite не перезапущен | `.env` в `frontend/`, перезапуск |
| 401 на приватном роуте | Cookie `pid` протухла или бэкенд перезапущен | Залогиниться заново |
| Позиция уезжает | Выставляем `currentTime` без пересчёта | Использовать `positionNow(state)` |
| Трек не переключается сам | Не отправлен `track_loaded` | Отправлять по `loadedmetadata` |

## 16. Сборка и деплой

**Production build**

```
cd frontend
npm run build
```

Результат — `frontend/dist/`.

**Локальный просмотр**

```
npm run preview
```

Открывается `http://localhost:4173`.

**Деплой**

`dist/` — статика. В репозитории лежит готовый `nginx.conf` для прод-варианта:
SPA-fallback + проксирование `/api/`, `/media/` и `/ws` на бэкенд. Docker-compose
сейчас поднимает dev-сервер Vite, поэтому файл ждёт «настоящей» сборки статикой
(или любого другого хостинга: Caddy, Vercel, Netlify, Cloudflare Pages).

Для SPA-роутинга нужен fallback на `index.html`. У каждого хостинга свой способ:

- Nginx — `try_files $uri $uri/ /index.html`;
- Netlify — файл `_redirects` со строкой `/* /index.html 200`;
- Vercel — `vercel.json` с rewrite всех путей на `index.html`.

**Production .env**

```
VITE_API_URL=https://api.listen-together.example.com
VITE_WS_URL=wss://api.listen-together.example.com/ws
```

Переменные с префиксом `VITE_` инлайнятся в бандл при сборке.

**WebSocket за прокси.** Nginx должен проксировать заголовки `Upgrade` и `Connection`, иначе WebSocket не поднимется. Без этого плеер будет работать, а синхронизация — нет.

## 17. Что дальше

MVP готов целиком: логин по нику, комнаты, плеер с синхронизацией, очередь, каталог с загрузкой, live-обновления.

Возможные следующие шаги (по приоритету):

1. Чат комнаты, реакции, публичные комнаты.
2. Мобильная адаптация, тёмная тема, PWA, Web Notifications.
3. Визуализация на Web Audio API, плейлисты из каталога, поиск по трекам.
